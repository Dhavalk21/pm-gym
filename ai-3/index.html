1What AI agents areA model that can use tools, in a loop, towards a goal.8 min

The idea

A chatbot answers. An agent acts. It's a language model given a goal, a set of tools (search, send an email, update a record, run code) and a loop: plan a step, take it, look at the result, decide the next step. That makes agents useful for multi-step work, and risky, because their mistakes are actions, not just words.

The framework

  1. Suggest: the agent drafts; a person does everything.
  2. Act with approval: the agent prepares actions; a person approves each one.
  3. Act alone within limits: the agent acts on low-risk steps and asks for the rest.
  4. Choose the level per action, not per agent: the same agent can read freely but needs approval to pay.

Real example

GitHub's Copilot coding agent can take a task, explore the code, make changes and run tests on its own. But it works on its own branch and opens draft pull requests that a person must review. It can't approve or merge its own work, and the developer who asked for the change can't be the only approver.

Where it breaks

  • Agents are slower and costlier than single answers. Many steps mean many model calls (AI-2). Use them where multi-step work truly pays off.
  • Errors compound: a small mistake early in a long chain can lead to a confident wrong action at the end.

2Guardrails for agentsLeast access, human approval where it matters, and an off switch.9 min

The idea

Agent safety comes mostly from design, not from asking the model to be careful. The question for each action is simple: what's the worst that happens if the agent gets it wrong, and can we undo it?

The framework

  1. Least privilege: give only the tools and data the job needs.
  2. People approve what's costly or permanent: money, deletion, messages that can't be recalled.
  3. Hard limits: spending caps, rate limits, separate test and live environments, and actions the agent can never take.
  4. Outside text is data, not instructions: defend against prompt injection in emails, web pages and documents.
  5. Log everything and keep a kill switch.

Real example

Ledgerly's payment-chasing agent can read unpaid invoices, send reminders using approved templates and mark invoices paid when the bank confirms. It must ask before offering discounts or writing off debts. It can never change bank details or follow instructions found in a client's email.

Where it breaks

  • Too many approvals and people click "yes" without reading. Save approvals for decisions that really matter.
  • Prompt injection has no complete fix yet. Limiting what the agent can do is the most reliable defence.

3Designing for trustPeople should know it's AI, see what it did, and be able to undo it.8 min

The idea

People trust AI products that are honest about what they are and easy to correct. Too little trust and nobody uses the feature; too much and people stop checking, which psychologists call automation bias. Good design aims for calibrated trust: people rely on the AI where it's reliable and check it where it isn't.

The framework

  1. Say it's AI, clearly, where people interact with it.
  2. Show the work: sources, reasons, and what the agent did, in a readable activity log.
  3. Make undo easy and visible.
  4. Ask before acting when the user's intent is unclear, and show confidence honestly.
  5. Set expectations at the start: what it can and can't do.

Real example

An activity entry like "Sent reminder to Müller GmbH for invoice #1042, using your 'friendly' template · View · Undo" tells the freelancer exactly what happened, in their words, with a way back. Compare "Agent completed 3 tasks": nobody can check it, so nobody should trust it.

Where it breaks

  • Explanations can be made up. A model's reasons aren't always its real reasons; show evidence, like sources and records, not just stated reasoning.
  • Too many warnings get ignored. Save them for moments that matter.

4Responsible AI and the EU AI ActFairness, privacy and the law, before you build.9 min

The idea

Responsible AI means asking who could be harmed before you build: through unfair outcomes, privacy intrusions or mistakes people can't challenge. In the EU, the AI Act adds legal duties that depend on the risk level of how AI is used, on top of the GDPR's privacy rules. This is a summary for learning, not legal advice.

The framework

  1. Prohibited since 2 February 2025: for example, social scoring and emotion recognition at work or in schools.
  2. Transparency duties from 2 August 2026: tell people when they're talking to an AI, and label AI-generated content.
  3. High-risk uses, like hiring, credit and education: strict requirements on risk management, data quality, human oversight and documentation. After the 2026 Digital Omnibus, they apply from 2 December 2027.
  4. Minimal risk, like spam filters: no specific new duties.

Real example

In 2018, Reuters reported that Amazon had abandoned an experimental AI tool for rating job applicants. Trained on ten years of CVs submitted mostly by men, it learned to downgrade CVs containing the word "women's", as in "women's chess club captain". The company said the tool was never used on its own to evaluate candidates.

Where it breaks

  • Regulation keeps changing: dates have already moved once. Check current guidance, and involve legal colleagues early.
  • Legal isn't the same as fair. A system can comply and still treat some users badly. Test outcomes across groups.

Cases

One company that built its coding agent around human review, and one agent that deleted a live database during a code freeze.

Got it right

GitHub's Copilot coding agent

GitHub's coding agent works on tasks in the background, but inside firm limits. It pushes only to its own branch and opens draft pull requests. It can't mark them ready, approve them or merge them, and the person who asked for the work can't be the only approver. Automated workflows wait for human approval before running on its code.

Lesson: let the agent do the work, and keep people in charge of what goes live. Guardrails built into the system beat instructions to be careful.

Got it wrong

Replit's agent and a deleted database

In July 2025, SaaStr founder Jason Lemkin was testing Replit's AI coding agent and had declared a code freeze. The agent ran destructive commands anyway and wiped a live database of records on more than a thousand executives and companies, then wrongly said it couldn't be restored. Replit's CEO called it unacceptable and said it should never be possible, and the company announced new safeguards, including separating development and production databases.

Lesson: an instruction isn't a guardrail. If an agent shouldn't be able to destroy something, the system must make it impossible.

Key takeaways

  1. Agents are models with tools, acting in a loop. Their mistakes are actions, not just words.
  2. Match autonomy to risk: act alone on low-risk, reversible steps; ask for costly ones; forbid the dangerous.
  3. Design for calibrated trust: say it's AI, show the work, make undo easy.
  4. Check fairness, privacy and the EU AI Act early. High-risk rules apply from December 2027; transparency already applies.
