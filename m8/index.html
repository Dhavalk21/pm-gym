Lessons

Each one runs the same way: the idea, the framework, a real example, where it breaks, and a quick drill.

1How a web app worksWhat actually happens when someone taps a button.9 min

The idea

Almost every product has three layers. The client (the app or browser) shows things and takes input. The server runs the logic. The database remembers things. They talk through requests and responses: the client asks, the server answers.

The framework

ClientApp or browser
ServerLogic and rules
DatabaseStored data

For any feature, ask three questions: what does the client need to show, what does the server need to decide, and what has to be stored or looked up?

Real example

A customer taps "Pay €42". The app sends the order to the server. The server checks the basket, asks a payment provider to charge the card, saves the order in the database, then tells the app to show "Order confirmed". Each arrow in that story is a place things can be slow or fail.

Where it breaks

  • Real systems have many more boxes: caches, queues, background jobs, dozens of services. The three layers are a map, not the territory.
  • "Just a small UI change" sometimes isn't: if the screen needs data that isn't stored yet, the work is in the other layers.

Drill: which layer?

Users want to see their order history from three years ago, but it was never saved. Where's the work?

2APIsThe contracts that let systems, and companies, work together.8 min

The idea

An API (application programming interface) is a contract: send this request, get this response. Your app talks to your server through APIs, and your server talks to other companies' services the same way: payments, maps, email, AI models.

The framework

  1. The contract: what you send, what you get back, what errors look like.
  2. Limits: how many requests per minute, and what it costs per call.
  3. Versions: APIs change. Good providers announce it; you still have to update.
  4. Dependency: when their API is down, your feature is down.

Real example

A delivery app uses a maps provider's API to show couriers on a map. When the provider raises its prices per map load, the cost of every order goes up overnight. When the API has an outage, tracking disappears for every customer. Neither is an engineering bug; both are product risks you can plan for.

Where it breaks

  • "There's an API for that" doesn't mean it's easy. Edge cases, limits and costs still need work.
  • Too many third-party dependencies make you fragile. Know which ones are critical and what happens when they fail.

Drill: spot the risk

Your app's most important feature depends on one external AI model API. What should a PM ask first?

3Data, speed and scaleSlow is a feature, and it's a bad one.8 min

The idea

Three technical qualities show up directly in the user experience: whether the right data exists and is correct, how fast things respond (latency), and whether it still works with many more users (scale).

The framework

  1. Data model: what things you store and how they relate, like users, orders and products. Hard to change later, so think early.
  2. Latency budget: decide how fast each key action must feel, and design for it.
  3. Scale: ask "what if ten times more people did this at once?" before a big launch or sale.

Real example

Speed changes behaviour. Google's research with mobile sites found that as page load time goes from one second to three, the probability of a visitor bouncing increases by 32%. For a PM, "make it faster" can be a bigger win than a new feature.

Where it breaks

  • Premature optimisation wastes time. Make the slow things that matter fast, not everything.
  • Averages hide pain. Look at the slowest 5% of requests too; that's where people give up.

Drill: which matters most?

A flash sale is planned for 10x normal traffic. What's the PM's most useful question?

4Tech debt, and build or buyShortcuts have interest. Not everything is worth building.8 min

The idea

Technical debt, a metaphor from programmer Ward Cunningham, means shortcuts taken now that make future changes slower, like interest on a loan. Some debt is a smart choice to ship faster; unpaid debt eventually slows everything down. Build or buy is the related question: should we make this ourselves, or use an existing product?

The framework

  1. Make debt visible: list it, estimate its "interest" (how much it slows work), and pay down the expensive ones.
  2. Build what makes you different. Buy what's standard: payments, email, login, analytics.
  3. Count the full cost: building means maintaining it forever, not just shipping it once.

Real example

A start-up builds its own login system to save a subscription fee. Two years later, two engineers spend part of every month on password resets, security updates and two-factor login. A login provider would have cost less than one engineer's time, and been more secure.

Where it breaks

  • Buying creates lock-in and dependency (lesson 2). Check exit costs before you commit.
  • "We'll fix it later" rarely happens without a plan. Reserve regular time for paying down debt.

Drill: build or buy?

A small team wants to build its own payment processing to avoid provider fees.

Cases

One company whose internal APIs became a business, one deployment that destroyed a firm in under an hour.

Got it right

Amazon's API mandate

Around 2002, Jeff Bezos reportedly required every Amazon team to share data and features only through service interfaces, APIs designed as if outsiders might use them. It was painful at first. It also meant Amazon's infrastructure was built as reusable services, which helped it offer those services to other companies as Amazon Web Services.

Lesson: clean contracts between systems let you move faster, and can open new products.

Got it wrong

Knight Capital

On 1 August 2012, the trading firm Knight Capital deployed new software, but one of its servers still ran old, unused code that the update accidentally switched back on. In about 45 minutes it sent millions of unintended orders and lost around $440 million. The firm needed a rescue and was acquired within months.

Lesson: tech debt (old code left in place) plus a risky deployment process can be fatal. Release safely, and be able to switch things off.

Key takeaways

  1. Every feature crosses client, server and data. Ask what each layer needs.
  2. APIs are contracts and dependencies. Plan for them being slow, down or pricier.
  3. Speed and scale are product decisions, not just engineering ones.
  4. Build what makes you different; buy what's standard. Keep tech debt visible.
